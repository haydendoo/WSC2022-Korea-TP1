# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A WorldSkills 2022 TP53 Day 1 ("IoT + AI + Web service") **practice starter kit** — it
reproduces what a competitor's AWS account looked like when the competition started (baseline
IAM only), not a solution to the challenge. The original spec is
`WSC2022SE_TP53_Day1_actual_en.pdf`; read it before making non-trivial changes.

This distinction governs almost every design decision in the repo and must be preserved:

- **Terraform provisions ONLY the baseline** a participant is given: `TeamRole` (Lambda
  execution role, per "attach TeamRole to your lambda function as the execution role") and
  `EC2Role` behind an instance profile literally named `ec2-prole` (per "attach EC2Role as
  ec2-prole for your EC2 instance" — reproduced verbatim even though it reads like a typo for
  "ec2-profile", because it's the literal name the spec instructs). No bastion, VPC, or network
  baseline — Day 1's spec never mentions a pre-existing instance.
- Terraform must **never** provision the participant's actual solution: the IoT Core Thing/
  certificate/policy, the S3 bucket, the Lambda function, Comprehend wiring, the DynamoDB table,
  or the EC2 instance running the web service. If a change starts to add one of these, stop —
  that's out of scope by design.
- `services/server` is a **from-scratch practice replacement** for the proprietary "server-stub"
  Go binary described in the spec, not the real binary and not a reverse-engineering of it.
  Don't try to make it byte-identical to anything; it just needs to satisfy the documented
  interface (see Architecture below).
- `certs/` (`root-CA.crt`, `GameDayThing.cert.pem`, `GameDayThing.private.key`) is a **shared,
  non-sensitive practice identity** — the same key pair every participant registers into their
  own AWS IoT Core account, mirroring how the real competition hands out one device identity to
  every competitor. It is intentionally committed to this repo. The companion
  `gameday-simulator` project's `wsc2022-korea-day1` scenario embeds a copy of the same files to
  act as the "IoT device" — if you regenerate certs via `scripts/gen-certs.sh`, re-copy `certs/`
  into that scenario's `dist/certs/` or the two will no longer match.

## Commands

### Go service (`services/server` — standalone module)

```bash
cd services/server && go build -o /tmp/server . && go vet ./...
```

No test suite exists. The binary supports `--help`; use it plus a manual `curl` against `GET /`
(expect HTTP 200) as the smoke test — see `scripts/verify.sh` for the pattern (spins up the
binary with a throwaway local config and curls it; `GET /` doesn't touch DynamoDB, so it works
without AWS credentials).

### Build / package / verify (from repo root)

```bash
./scripts/build.sh     # compiles server for linux/amd64 into dist/
./scripts/verify.sh     # builds, then runs --help + GET / checks
./scripts/package.sh    # runs build.sh, assembles the rest of dist/ (config, table.json,
                         # certs/, dist/README.md), and builds a Docker image if Docker is
                         # available
```

`dist/` is entirely generated by `scripts/package.sh` — never hand-edit files under it; edit the
source under `services/`, `config/`, `database/`, or `certs/` and re-run the script. There is no
`.gitignore` in this repo, so `dist/` (including the compiled binary) is currently
untracked-but-not-ignored; be deliberate before `git add`-ing it.

### Terraform (`terraform/`)

```bash
cd terraform
terraform init
terraform fmt -recursive
terraform validate
terraform plan
```

`terraform plan`/`apply` make real AWS API calls (caller identity, etc.) and `apply` creates real
billable-adjacent IAM resources — never run `apply` without the user's explicit go-ahead.
`terraform validate` and `plan` are safe to run freely for verifying changes. Default region is
`ap-southeast-1` (`variables.tf`).

### Docker Compose (local practice stack, no AWS required)

```bash
docker compose -f docker/docker-compose.yaml up --build
curl localhost:8080/
```

Uses `config/server.local.json` (points at DynamoDB Local via `DynamoEndpoint`) — different from
`config/server.example.json`, which documents the real-AWS config shape and is what ships in
`dist/`. A one-shot `create-table` service creates the `unicorn` table in DynamoDB Local before
`server` starts.

### Regenerating the shared IoT certificate

```bash
./scripts/gen-certs.sh   # overwrites certs/root-CA.crt, certs/GameDayThing.{cert.pem,private.key}
```

Only do this deliberately — see the "shared, non-sensitive practice identity" note above. After
regenerating, re-copy `certs/` into `gameday-simulator`'s embedded scenario `dist/certs/`.

## Architecture

### Config loading (`services/server/config.go`)

Unlike Day 2's root/stub (which fetch from AWS AppConfig), the Day 1 spec never mentions
AppConfig — `server` resolves `--table`/`--region`/`--port` purely from flags/environment
variables, optionally defaulted from a local JSON file (`--config`, default `config.json`) for
local testing (docker-compose, `verify.sh`). `--dynamo-endpoint` overrides the DynamoDB endpoint
URL — a local-dev-only convenience for DynamoDB Local, never set against real AWS.

### Service dependency (`services/server/dynamodb.go`)

`server` only reads: `GET /unicorn/{id}` runs a DynamoDB `Query` on partition key `id` against
the `unicorn` table (partition key `id`, sort key `sentiment` — name/schema fixed by the spec's
Database section, see `database/table.json`), returning every `{id, sentiment, message}` item
found. `GET /` / `GET /healthz` are a pure health check with no DynamoDB dependency, so they work
even before the table exists — matches the spec's "once you get HTTP 200 response... it attests
that your application is running normally" framing used across the WSC2022 TP53 days.

### Terraform structure (`terraform/`)

`iam.tf` is the only substantive file — read its header comments before editing. `versions.tf` /
`providers.tf` / `variables.tf` / `outputs.tf` / `main.tf` are standard scaffolding, mirroring the
companion Day 2 repo's layout. No `baseline.tf`/`bastion.tf` exist here — Day 1 has no
pre-provisioned network or instance.

### `certs/` and `scripts/gen-certs.sh`

Generates a self-signed CA (`root-CA.crt`) and a device certificate/key signed by it
(`GameDayThing.cert.pem` / `GameDayThing.private.key`) using `openssl`. This is *this practice
kit's own* CA, not AWS's production Amazon Root CA — that's fine, because `root-CA.crt`'s only
required role per the spec is "one of the three files uploaded to S3"; the actual TLS trust
anchor used when the gameday-simulator "IoT device" validates AWS IoT Core's server certificate
is the operating system's/Go's standard trust store, not this file. Participants register
`GameDayThing.cert.pem` via `register-certificate-without-ca` (no CA registration ceremony
needed) — see the top-level README for the full command sequence.
